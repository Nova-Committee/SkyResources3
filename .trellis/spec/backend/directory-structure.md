# Directory Structure

> How backend and mod runtime code is organized in this project.

---

## Overview

SkyResources3 is currently a compact single-mod NeoForge project. Backend code means Java mod code that runs through NeoForge lifecycle events, registries, config loading, data generation, or server/client setup. There are no HTTP endpoints, services, controllers, or database layers.

The current structure favors simple NeoForge conventions:

- One Gradle project.
- One base Java package: `committee.nova.mods.skyresources3`.
- One mod id and resource namespace: `skyresources3`.
- Main mod bootstrap in `Skyresources3.java`.
- Common config definition and load handling in `Config.java`.
- Deferred registries under `registry/`.
- Data generation providers under `data/`.
- Custom server-side processing recipe models under `recipe/`.
- Generated mod metadata from `src/main/templates`.

## Directory Layout

```text
.
|-- build.gradle
|-- gradle.properties
|-- settings.gradle
|-- src/
|   |-- main/
|   |   |-- java/
|   |   |   `-- committee/nova/mods/skyresources3/
|   |   |       |-- Config.java
|   |   |       |-- Skyresources3.java
|   |   |       |-- data/
|   |   |       |-- recipe/
|   |   |       `-- registry/
|   |   |-- resources/
|   |   |   |-- assets/skyresources3/
|   |   |   |   |-- blockstates/
|   |   |   |   |-- items/
|   |   |   |   |-- lang/en_us.json
|   |   |   |   |-- models/
|   |   |   |   `-- textures/
|   |   |   `-- skyresources3.mixins.json
|   |   `-- templates/
|   |       `-- META-INF/neoforge.mods.toml
|   `-- generated/resources/        # generated by the data run, when present
```

Important Gradle wiring:

- `sourceSets.main.resources { srcDir 'src/generated/resources' }` includes generated resources.
- `generateModMetadata` expands properties from `gradle.properties` into `src/main/templates/META-INF/neoforge.mods.toml`.
- `sourceSets.main.resources.srcDir generateModMetadata` includes generated metadata in the main resource set.

## Module Organization

Use the current flat package while the feature set is small:

- `Skyresources3.java` owns mod bootstrap, registration into the mod event bus, and current lifecycle event handlers.
- `Config.java` owns `ModConfigSpec` declarations, config value validation, and config load copying into runtime static fields.
- `registry/` owns deferred registry declarations for blocks, items, creative tabs, and future registry groups.
- `data/` owns NeoForge data generation entry points and providers for recipes, loot tables, and tags.
- `recipe/` owns common custom recipe data models, codecs, runtime inputs, and lookup helpers. Keep client recipe displays and JEI/EMI integration outside this package.

When a feature becomes too large for the current two-class layout, create a package under `committee.nova.mods.skyresources3` that matches the feature responsibility. Keep package names lowercase and singular unless the existing Minecraft/NeoForge convention is plural.

Recommended split points once needed:

- Feature-specific packages for behavior classes, block entities, menus, entities, networking, commands, or world generation.
- `config` if config grows beyond the current `Config.java`.
- `mixin` for mixins declared by `skyresources3.mixins.json`.

Do not introduce layered web-application names such as `controller`, `repository`, or `dto`; this project is a Minecraft mod, not a service backend.

## Naming Conventions

- Java packages use lowercase names and stay under `committee.nova.mods.skyresources3`.
- The mod id and resource namespace are `skyresources3`.
- Registry ids use lowercase snake case, for example `example_block` and `example_item`.
- Deferred registry constants use uppercase snake case, for example `EXAMPLE_BLOCK`, `EXAMPLE_BLOCK_ITEM`, and `EXAMPLE_ITEM`.
- Config spec constants use uppercase snake case, for example `LOG_DIRT_BLOCK` and `MAGIC_NUMBER`.
- Runtime config values use lower camel case, for example `logDirtBlock`, `magicNumber`, and `magicNumberIntroduction`.
- Translation keys include the namespace, for example `block.skyresources3.example_block`, `item.skyresources3.example_item`, and `itemGroup.skyresources3`.
- Mixin config stays named `skyresources3.mixins.json`; mixin classes belong under `committee.nova.mods.skyresources3.mixin`.

Keep `gradle.properties`, `Skyresources3.MODID`, resource directories, translation keys, and metadata templates aligned when changing identity or naming.

## Resource and Data Generation Layout

- Manual client resources live under `src/main/resources/assets/skyresources3`.
- Minecraft 1.21.11 item definitions live in `assets/skyresources3/items/<id>.json` and point to `skyresources3:item/<id>` or `skyresources3:block/<id>` model ids.
- Item models live under `assets/skyresources3/models/item/`; flat icons use `minecraft:item/generated`, handheld tool-like icons use `minecraft:item/handheld`.
- Textures live under `assets/skyresources3/textures/item/` or `assets/skyresources3/textures/block/`.
- Generated server data lives under `src/generated/resources/data/` and is produced by `gradlew.bat runData`.
- Generated custom process recipes live under `src/generated/resources/data/skyresources3/recipe/process/<process>/<name>.json`.
- Generated resources should be committed when they are part of the runtime data pack. Do not commit `.cache` files created by the data generator.

### Legacy Metadata Item Families

When porting old 1.12.2 items that used metadata for many visible variants, split them into standalone 1.21.11 item
ids instead of recreating metadata-style containers. Keep a small typed enum as the single source of truth when later
recipes need the same legacy ordering or metadata:

```java
public enum ExampleFamily {
    IRON("iron", "Iron");

    public String itemId() {
        return this.id + "_example_item";
    }
}

public static final Map<ExampleFamily, DeferredItem<Item>> EXAMPLE_ITEMS = registerExampleItems();
```

Each standalone item must still have its own `assets/skyresources3/items/<id>.json` definition and translation key. Use
a shared item model and texture only when the old item also shared a base asset or the task explicitly defers variant
tinting.

## Examples

Existing examples to follow:

- `src/main/java/committee/nova/mods/skyresources3/Skyresources3.java` shows the mod entry point, `DeferredRegister` usage, creative tab registration, and lifecycle event hooks.
- `src/main/java/committee/nova/mods/skyresources3/Config.java` shows the current `ModConfigSpec` pattern and config load event handling.
- `src/main/java/committee/nova/mods/skyresources3/registry/ModItems.java` shows deferred item registration and resource id naming.
- `src/main/java/committee/nova/mods/skyresources3/registry/ModRecipeTypes.java` shows custom recipe type and serializer registration.
- `src/main/java/committee/nova/mods/skyresources3/recipe/SkyResourcesProcessRecipe.java` shows the data-driven processing recipe codec and matching contract.
- `src/main/java/committee/nova/mods/skyresources3/data/SkyResources3RecipeProvider.java` shows the current 1.21.11 recipe provider runner pattern.
- `src/main/templates/META-INF/neoforge.mods.toml` shows metadata values expanded from Gradle properties.
- `src/main/resources/assets/skyresources3/lang/en_us.json` shows namespaced translation keys.
- `src/main/resources/skyresources3.mixins.json` shows the mixin config package and Java 21 compatibility level.
